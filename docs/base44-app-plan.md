# תיקון האתר "עוזר הנדסי – ניהול פרויקטים" — מעבר משיטת תיקון-שורה לשיטת מקור-אמת

## Context — למה אנחנו עושים את זה

אביחי עצר את העבודה אחרי יום של תיקוני UI ואמר: "מרגיש לי שיש המון פערים באתר, לתקן את זה זה פינג-פונג שלא נגמר... אין מוח שיודע להכווין את הנתונים מהאקסל הראשי לאתר, וחישוב שם לא נכון ויש תצוגת מספרים שלא אמיתיים."

הוא צודק, אבל **לא בדיוק מהסיבה שהוא חשב**. בדיקה מלאה של כל הישויות ב-Base44 העלתה:

### מה שדווקא תקין (נבדק, מתכנס לאגורה — פרויקט 2288)
```
הכנסות   3,972,804  = Σ 37 שורות ClientInvoice.current_indexed      ✓
קבלנים   3,487,613  = Σ 9 ContractorInvoice + Σ 7 PurchaseOrder     ✓
תקורות      77,187  = Σ 43 שורות Overhead.net                       ✓
הוצאות   3,564,800  = 3,487,613 + 77,187 + 0                        ✓
רווח       408,004  = 3,972,804 − 3,564,800  (10.27%)               ✓
```
**האריתמטיקה נכונה.** ההנחה הראשונית שהחישוב שבור הייתה שגויה.

### למה הפינג-פונג
בתוכנית החינמית אין לי גישה לקוד. כל תיקון = הוראה עיוורת לבונה + קרדיטים + אביחי מצלם מסך ומדווח. בסאגת ה-RTL זה לקח 4 סבבים: 3 תיקנו סימפטומים, הרביעי גילה ש-`direction: rtl` היה כלוא ב-`@layer base` ונדרס ע"י Tailwind. **עם גישת קריאה לקוד הסבב הראשון היה מוצא את זה.**

## Phase 0 — לשחרר את החסימה  *(אביחי: 2 דקות)*

אביחי מנפיק **Personal API key** ב-Base44 ומוסר לי אותו.

### הנתיב המדויק (אומת מול ה-UI)
**`Secrets` → לשונית `Personal access tokens` → `+ Create access token`**
לבחור את האפליקציה "עוזר הנדסי – ניהול פרויקטים", הרשאות קריאה+כתיבה. הטוקן מוצג **פעם אחת בלבד**. ניתן לביטול מאותו מסך בסיום.

### ⚠️ מלכודת: יש שני סוגי מפתחות ורק אחד מהם עובד
| | מאיפה | מה הוא נותן |
|---|---|---|
| **Personal access token** ✅ | `Secrets` → לשונית **Personal access tokens** | קריאה **וכתיבה** של קוד |
| Workspace API Key ❌ | `Secrets` → לשונית **Workspace API Keys** | נדחה ב-403 על `write-batch` |
| App/SDK key ❌ | Dashboard → **API Documentation** | גישה לנתוני האפליקציה בלבד |

התיעוד של Base44 על `write-batch` מפורש: *"This endpoint accepts a personal API key. **Workspace API keys are not authorized** for it and are rejected with a 403."*
**המסך "API Documentation" ב-Dashboard הוא המקום הלא נכון** — הוא מתעד את ה-SDK של האפליקציה, לא את מפתח המפתחים.

### מסלול גיבוי אם לא נמצא מפתח אישי
להוריד את קוד המקור כ-zip מהעורך של Base44 ולהעלות לי אותו כאן. נותן **קריאה מלאה בלי שום מפתח** — מספיק כדי לסיים את הניחושים. התיקונים ימשיכו דרך הבונה.

### ✅ תוצאות Phase 0 (בוצע 22/09, טוקן `Claude Code`, scope = אפליקציה אחת, Full access)

| יכולת | מסלול | תוצאה |
|---|---|---|
| **כתיבת קוד** | `POST /api/apps/{id}/coding/write-batch` | ✅ **עובד.** אומת — `updated_date` קפץ ל-10:04:36. עד 50 קבצים בקריאה, **בלי קרדיטים** |
| קריאת קוד | `POST .../sandbox-bridge/read_file` | ❌ **402** — Builder plan required |
| קריאת קוד | `GET .../coding/export-to-zip` | ⚠️ לא חסום בתוכנית, אבל מחזיר zip בינארי שה-MCP לא מעביר, ו**רשת הסביבה חוסמת את base44.com** (`403 CONNECT`) |
| GitHub | `GET .../github/organizations` | ❌ **402** — not available on plan |

### 🔴 האסימטריה המסוכנת
**יש כתיבה, אין קריאה.** זה גרוע יותר מהמצב הקודם — הבונה לפחות קורא את הקוד לפני שהוא משנה. **לא כותבים קוד בעיוורון.** חובה לפתור את הקריאה לפני שמשתמשים ב-`write-batch`.

### הפתרון: אביחי מוריד את ה-zip ומעלה לכאן
הייצוא **לא חסום** בתוכנית — רק לא נגיש לי מהסביבה הזו. אביחי מוריד את קוד המקור מהעורך של Base44 ומעלה לצ'אט. אז:
```
zip → אני קורא את כל הקוד → עריכה מדויקת → write-batch → בלי קרדיטים, בלי ניחושים
```
**חיסרון:** ה-zip הוא צילום-מצב. אם הבונה ישנה משהו אחר כך, העותק שלי מתיישן. מאחר שמעכשיו הכתיבה עוברת דרכי, זה נשלט — ונבקש zip טרי בכל פעם שהבונה כן ירוץ.

### ✅ ההחלטה: פותחים את הרשת ל-base44 (נבחר 22/09)

**מה אביחי עושה:**
1. claude.ai/code → הגדרות הסביבה → מדיניות רשת / רשימת דומיינים מותרים → להוסיף `app.base44.com` ו-`base44.com`
   (תיעוד: https://code.claude.com/docs/en/claude-code-on-the-web)
2. לפתוח **סשן חדש** — המדיניות נכנסת לתוקף ביצירת הקונטיינר, לא על סשן שכבר רץ

**מה הסשן החדש עושה מיד:**
```bash
curl -H "api_key: $TOKEN" \
  "https://app.base44.com/api/apps/6ab20d2348945293cb5f075e/coding/export-to-zip" \
  -o app.zip && unzip app.zip
```
(אם `api_key` לא עובד — לנסות `Authorization: Bearer $TOKEN`. שני הפורמטים לא נבדקו כי הרשת חסמה.)

למיומנות `project-2288-document-intake` יש **נוהל מתועד ועובד** שקולט מסמכי מקור (גיליונות שירות, חשבוניות אמבל/מונטיה/ע.הנדסה, דוחות פריורטי) ומעדכן את האקסל של 2288. יש לו יומן קליטה, גיבוי אוטומטי, ובדיקת התאמה מול פריורטי.

**"המוח שמכווין את הנתונים" שאביחי ביקש — קיים כבר עד האקסל. חסרה רק החוליה האחרונה:**

המייבא **יושב במורד הזרם ולא מחליף כלום.** האקסל נשאר מקור האמת, הנוהל הקיים נשאר כמו שהוא.

**שני כללים שאני מאמץ מהנוהל הקיים** (הם כבר הרגלי העבודה של אביחי):

**אילוץ טכני שצריך להכריע:** הנוהל הקיים רץ עם `device_bash` על המחשב של אביחי. בסשן הזה אין לי `device_bash` — רק `mcp__ms365__` (OneDrive) ו-`mcp__Base44__update_entities`. צריך להחליט אם המייבא רץ מכאן דרך OneDrive, או מצטרף לסקיל הקיים שרץ אצלו.
